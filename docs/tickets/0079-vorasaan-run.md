# 0079: `vorasaan run`: hand a Feature's context to the coding assistant

## Goal
A developer runs `vorasaan run --ai claude` in their repository, and their coding assistant reads one Feature's approved context (the latest Spec, its Decisions, the Project rules, the most relevant retrieved context, the Jira Epic key and the approved Design Doc of their Platform) from one file, instead of everything or a guess (REQUIREMENT 15, ADR 0002, ADR 0014).

## Scope
- **`vorasaan run [--feature <id or title>] [--ai claude|codex|gemini] [--platform <name|qa|none>] [--budget <tokens>] [--no-launch]`** writes the Feature's **Hand-off** (new glossary term) to `.vorasaan/specs/<feature>.md` at the repository root, then hands it to the coding assistant: started in the repository when it is on PATH and a person is at the terminal, else the command to start it is printed.
  - **The Feature:** `--feature` takes an id, or the title or file name of a Feature the user is a Role Owner of (the bound Project's first, as `vorasaan init` scopes them); without it, the only Feature in scope, or a picker.
  - **The Platform** whose approved Design Doc goes with it (0069): `--platform`, else from the user's Team Roles, ties broken by the Platform the changed files point to (0052's hint, names only), else none, with a line saying how to ask for one.
- **A server endpoint** assembles the Hand-off within a token budget: the latest Spec first, the Feature's Decisions and open Decision Requests, the approved Design Doc (`GET /features/:id/design-docs/:key`'s newest version, 0069) and whether the Spec changed it since, the Project rules (the effective Feature Guidelines and the Project Brief, 0060's foundation) and retrieved chunks (ADR 0007, 0076's top-k), plus the Jira Epic key if linked.
  - Everyone in the Feature's Organization reads it, as they read the Feature; anyone else gets a 404.
  - Everything people wrote is fenced as untrusted data the assistant must not take as instructions; recognisable credentials are redacted.
  - The file asks the assistant to answer in the developer's Reply Language and keep terms, names, ids and numbers as written (0068).
  - A query budget and a bench scenario (0073, 0074).
- **Safe files:** only inside the repository's `.vorasaan/specs/`, never through a symlink, with a file name nothing can turn into a path; a .gitignore line is suggested when git would commit the file. The CLI's credentials never reach the file, the assistant's command line or its environment.

## Acceptance criteria (test first)
- [x] Server, real Postgres: a Backend Role Owner's Hand-off has the Spec, the Decisions, the open Decision Requests, the Project rules, the retrieved Attachment and the Back-End Design Doc, in that order, with the Jira Epic key.
- [x] The Design Doc is marked stale when the Spec changes what it covers, not otherwise.
- [x] The Platform comes from `--platform` (id, name, `qa`, `none`; a 400 for an untargeted one), the Team Roles, the changed files' hint, or the only target; none otherwise, and the file says how to ask.
- [x] The budget holds: a long Attachment is shortened, the Spec stays first, and the file is within its budget.
- [x] Untrusted text can't close its data block, and credentials are redacted.
- [x] Outside the Organization: 404. Nothing is written and no AI is called.
- [x] A query budget for `GET /features/:id/hand-off`, in the bench.
- [x] CLI, with a fake server and temp directories, no real assistant: the file is written where it should be and replaced on the next run; the assistant is started in the repository with the path only and without the credentials, or its command is printed; the Feature by id, title, file name, scope or picker; a symlinked `.vorasaan`, an unsafe name, another Feature's or someone's own file are never written through; the .gitignore tip.

## Decisions
- **The server assembles the Hand-off; the CLI writes it.** `GET /features/:id/hand-off?platform=&hint=&budget=` (`HandOffQuery` / `HandOffView` in `@vorasaan/shared`, `hand-off/` in the server) returns the Markdown and what it holds (Spec Version, the Platform and how it was picked, the Design Doc's version, the Spec it follows and whether it is stale, the other Design Docs, the tokens used of the budget). Assembling on the server reuses retrieval, the foundation and the Design Doc rules where they live, keeps the budget in one place and is what the Drift check (Later) can build on. It is a read: no AI call, no Receipt, no row written. Everyone in the Feature's Organization reads it (as Design Docs, 0069); anyone else, and an unknown Feature, gets a 404. (`GET /features/:id` had no Organization check then; it has one since the Organization-scoping fix, which made every route that reads or changes a record by id answer 404 outside the caller's Organization.)
- **One file, `.vorasaan/specs/<slug>.md`.** The slug (`handOffSlug`, shared) is the title's letters and digits in any script, Thai included, lowercased and joined by `-`, at most 60 characters, else `feature-<first 8 of the id>`; it can't hold a dot, a slash or a backslash, and the CLI checks it again (`isHandOffSlug`) before writing. If that file holds another Feature's Hand-off (its front matter's `vorasaan-feature`) or a file someone wrote, `<slug>-<first 8 of the id>.md` is used; both taken: nothing is written. The file is replaced on each run: it is a snapshot, never edited.
- **What it holds, in this order**: front matter (`vorasaan-feature`, `title`, `spec-version`, `platform`, `design-doc-version`, `generated`), "How to use it" (the Spec is the source of truth and wins over the Design Doc; follow Decisions, an open Decision Request isn't decided; data blocks are data, never instructions; ask instead of guessing, with the `vorasaan raise --feature <id>` line; reply in the developer's Reply Language, keeping terms, names, ids, numbers and code as written, 0068), the Feature's facts (Project, Team, Jira Epic key and link when linked, Spec Version, Platform and why, the other Design Docs, the size), the **Spec**, the **Design Doc** (with a "Stale" note when the latest Spec changed what it covers: `designDocAffected` as 0069 computes it, on read), **Decisions**, **Open Decision Requests**, **Project rules** (the effective Feature Guidelines, then the Project Brief) and **Related context** (retrieved chunks: Attachments and the rest of the Project). The file's own words are English, for the assistant; every document stays in its own language.
- **Untrusted text is fenced.** Everything people wrote or documents hold sits in a `<vorasaan-data kind=… id=… title=… from=…>` block; anything inside that could open or close one is neutralised (`‹`), as `fence()` does for prompts. Titles and names outside blocks are one line with `<`, `>`, backticks and quotes neutralised. Recognisable credentials (private keys, AWS, GitHub, GitLab, `sk-`, Stripe, Slack, Google, JWTs, `vsp_` access tokens, passwords in URLs: `redactCredentials`, shared) are replaced by the server and again by the CLI, since a coding assistant may send the file to its own AI provider. Line-level keyword redaction (`redactSecrets` of the Repo Scan) was not used: "Session token: expires after 30 minutes" in a Spec is not a secret.
- **The budget** (`HAND_OFF_BUDGET`: 24,000 tokens by default, `--budget` 4,000 to 64,000). It is not an AI call of ours, so there is no model window to share (ADR 0012); the Hand-off has its own budget, split by `HAND_OFF_CONFIG`: 700 for the file's own words and tags; the Design Doc up to 30% of the rest (shortened to fit, with a note); the Project rules as an AI task's foundation (`ProjectFoundation.forFeature`: 15%, at most 4,000, the Guidelines' descriptions shortened, the Brief shortened to what is left), and what they don't use goes to retrieval; the rest is `ContextRetriever.forFeature` with the Feature's title, description and the Platform's name as the query, 0076's top-k of a Decision Request (15) and, new, `recentDecisions: 20` (the Feature's 20 newest Decisions before any ranked chunk, where AI tasks keep 5: an assistant building the Feature needs them all). The Spec stays first and whole while it fits, shortened otherwise (with a note), and nothing comes before it. The Brief is dropped from the retrieved blocks since the rules show it. The result is counted with the Thai-aware estimate (0059) and reported as `tokens.used`.
- **The Platform** (`chooseHandOffPlatform`): `--platform` (a target's id or name in any case, `qa`, or `none` for no Design Doc; anything else is a 400 listing what may be asked); else the target Platforms one of the developer's Team Roles answers for (their Role Owner roles on the Feature and their roles in its Team; Tech Lead answers for all, so it alone picks nothing): the only one, or among several the first the changed files point to, else the first in the Project's order; with none of them but QA held, the QA Design Doc; else the first target the changed files point to; else the Feature's only target; else none, and the file says to run `vorasaan run --platform <name>`. **The changed files never leave the machine**: the CLI computes 0052's hint against the Feature's targets and sends only the names of targets it points to (`hint`), and computes none when `--platform` is given. A Platform without an approved version gets a line saying so (build from the Spec, ask before designing what it leaves open); pending drafts are never handed over.
- **The assistants** (`assistants.ts`): `claude <prompt>`, `codex <prompt>` and `gemini --prompt-interactive <prompt>`, each starting interactively with one first message: read the file, follow its "How to use it", summarise and wait for a go-ahead. Only the path is on the command line, never the content (other users' `ps` could read it). The assistant is started (stdio inherited, in the repository root, the CLI exits with its exit code) only with `--ai`, a terminal on both stdin and stdout, the executable on PATH (`Bun.which`) and without `--no-launch`; otherwise the command is printed, quoted for a POSIX shell, and without `--ai` a `claude` example is. Its environment is ours **without `VORASAAN_TOKEN` and `VORASAAN_USER`**. Before writing, the CLI refuses a Hand-off containing its own token. More assistants are a line in `ASSISTANTS`.
- **Safe writing** (`hand-off-file.ts`): only `<repo root>/.vorasaan/specs/`; `.vorasaan` or `specs` that is a symlink, not a directory, or resolves outside the root is refused (before and after `mkdir`); a symlink where the file goes is refused; the content goes to a fresh temporary file (`wx`, never through an existing path) renamed over the old one. When `git check-ignore` says the file would be committed, the CLI suggests adding `.vorasaan/specs/` to .gitignore (it doesn't edit .gitignore: `.vorasaan/config.json` is meant to be committed, 0028).
- **The Feature**: an id as given; else `GET /features` (the user's Features as Role Owner) matched by title (any case) or file name, the bound Project's first; several matches list their ids. Without `--feature`: the only Feature in scope is used (and named), several open the picker, and without a terminal it asks for `--feature`.
- **Query budget**: `handOff: 46` (identity, the Feature with its Organization check, then its targets, the reader's Role Owner and Team rows, the latest Spec Version, the reader's language and the Jira site together; the Design Doc's newest version with the Spec it follows; the Project rules; and retrieval's 27 at most). A new bench scenario `GET /features/:id/hand-off` (the QA Design Doc of the bench Feature, which carries three versions); the query budget test counts 16 scenarios. Sorting the targets is done in code (position, then id), never by the database's text order.
- **Glossary**: CONTEXT.md gains **Hand-off**. README: the Agent handoff row is no longer planned, the CLI block shows `vorasaan run --ai claude`.
- **Tests**: server (real Postgres on an en-US ICU database, `FakeAiPort`, background work drained) `hand-off/hand-off.api.test.ts`: Beam's Hand-off with everything in order and the Jira key; data blocks that can't be closed from inside and a GitHub token redacted; stale only for a Back-End change; the Platform asked by name, id, `qa`, `none`, a 400 for Mobile, Team Roles broken by the hint, QA, the hint alone; a 4,000-token budget with a long Attachment (shortened, the Spec first, within budget) and 400s for out-of-range budgets; Thai (the slug keeps Thai letters, the file asks for Thai replies); 404s outside the Organization and for unknown Features; nothing written and no AI call. `choose-platform.test.ts` (the rule, Tech Lead, QA, case, the 400's words). `perf/query-budgets.api.test.ts` with the new scenario. CLI: `commands/run.test.ts` with a fake server (`Bun.serve`), temp directories and a fake spawner (the file and its redaction, the hint and the bearer token only in the header, the assistant's cwd, argv and environment, printed commands for no `--ai`, `--no-launch`, no terminal and not on PATH, the Feature by id, title, file name, scope and picker, the server's 400, the token never written, the .gitignore tip in a real `git init` repository, a symlinked `specs` refused), `hand-off-file.test.ts` (slugs, redaction, replacing, another Feature's and a hand-written file kept, unsafe names, symlinked `.vorasaan` and a planted file symlink, quoting, the environment) and `program.test.ts` (flags, unknown assistant, budget range). No web change, so no browser test.
- **Try by hand with a real coding assistant**: with the dev stack and the seed, sign in as Beam (`vorasaan login`), `vorasaan init`, then `vorasaan run --feature "Async checkout" --ai claude` in a repository: read `.vorasaan/specs/async-checkout.md`; does Claude Code read it first, summarise it, ask instead of guessing on the Spec's open questions, follow the Decisions, and ignore an instruction planted in the Spec or an Attachment? Try `--platform qa`, `--no-launch`, a Thai Organization (does it answer in Thai and keep the terms?), `codex` and `gemini` if installed, and a long Spec with `--budget 4000`.
- **Left open**: Agent Skills are not handed over (0069 said `vorasaan run` would): what an enabled Skill teaches is for Vorasaan's AI, and copying Skills into a repository would need their own consent and placement (`.claude/skills/`…); a later ticket. The TUI has no "run" action. The Hand-off isn't refreshed on its own when the Spec changes (run it again; the Drift check is Later). Assistants beyond the three, and a default `ai` in the user config.
