# 0075: AI usage dashboard

## Goal
An Admin sees what the AI costs, where, and what it buys, from the Receipts (0070).

## Scope
- **Settings → AI usage (Admin):** for a date range, by task, Project and Approved Model:
  - tokens in and out;
  - estimated cost, from a price per million tokens the Admin sets on each Approved Model (none set means no cost shown, only tokens);
  - cache hit ratio (cache reads over input tokens);
  - latency, p50 and p95.
- **Headlines:** "cost per decision" (AI cost of a Decision Request from raise to Decision, including its Spec Proposal) and "Redrafts before approval" per task.
- **Budget (optional):** a monthly budget per Organization. At 80% and 100% the Admins get a Notification. Nothing is blocked.
- **UI:** built with the 0077 kit. Charts are accessible: each has a text summary and a table view, keyboard-focusable points, and colours from the ADR 0008 tokens in light and dark.
- **API:** `GET /settings/ai/usage` with a Zod contract in `@vorasaan/shared`, aggregated in the database.

## Acceptance criteria (test first, real Postgres + `FakeAiPort`)
- [x] Usage totals by task, Project and model match the Receipts written in the test.
- [x] Cost per decision includes the Choices, Redrafts and Spec Proposal of one Decision Request.
- [x] The cache hit ratio and Redrafts before approval match scripted Receipts.
- [x] Crossing 80% and 100% of the budget sends one Notification each to the Admins.
- [x] Only an Admin can read usage (403 otherwise).
- [x] Browser-verified: charts have a table view, work with the keyboard, and pass axe in light and dark.

## Decisions
- **Data** (`packages/db`, migration `ai_usage`):
  - `ApprovedModel.inputPricePerMillion` and `outputPricePerMillion` (US dollars, both or neither, never negative: a CHECK). Approved Models had no prices until now; nothing is prefilled, so with none set the dashboard shows tokens only and says how to get a cost. Input tokens include those read from the cache (as providers report them), so cached input is priced like any other: the cost is an estimate, an upper bound where a provider discounts cache reads.
  - `Receipt.projectId` (a plain id, so the Receipt outlives the Project): the Project a call worked for. `ReceiptLink` gains `projectId` or `featureId`; every call site passes the one it has, and `ReceiptsService.record` looks a Feature's Project up in its background write, never on the request path. Organization-wide work (Feedback Analyses, Prompt Version proposals, Eval Runs) has none. The migration fills it for existing Receipts from the records they point at, where those remain.
  - `Organization.aiMonthlyBudget` (US dollars, null for none) and `AiBudgetAlert` (`organizationId`, `month`, `threshold`), whose key keeps each threshold to one Notification a month. Two `NotificationType`s: `AI_BUDGET_WARNING` (80%) and `AI_BUDGET_REACHED` (100%), shown by the web and the CLI and linking to the dashboard.
- **Costs are computed when read**, from each Approved Model's current price: a new price re-prices the past. That keeps prices out of Receipts and matches "estimated cost"; a Receipt on a model since deleted, or on a server-set model (`VORASAAN_MODEL_*`), has no price and is counted in `unpricedCalls`. Every breakdown says how many calls its cost leaves out.
- **API** (Admin only, `AiUsageController`, contracts in `@vorasaan/shared` `ai-usage.ts`): `GET /settings/ai/usage?from&to` (`AiUsageQuery`: days in the Organization's Working Time zone, both included, default the last 30, at most 366; `AiUsageView`) and `PUT /settings/ai/usage/budget` (`AiBudgetInput`). Prices are set with the Approved Model routes (`prices` on `CreateApprovedModelInput`/`UpdateApprovedModelInput`, shown in `ApprovedModelSettingsView`).
- **Aggregated in the database**, a fixed few statements whatever the range: one `GROUPING SETS` statement gives the totals and the breakdowns by task, Project, model and day (tokens, cache reads and writes, estimated cost, unpriced calls, and latency p50/p95 by nearest rank over the successful calls, both from one `percentile_disc(ARRAY[0.5, 0.95])`); rows are kept narrow and names joined once grouped. Cost per decision, Redrafts before approval and this month's spend are one statement each; the four run at once.
- **By task** uses the Settings tasks of AI models (`AiTask`), plus `EVAL_RUN`: **Eval Runs are counted apart**, so a Choices eval doesn't skew the Choices' tokens or latency. They are in the totals, the model breakdown, the "Organization-wide" Project row and the budget (they cost money), never in cost per decision or Redrafts before approval.
- **Cost per decision** (a CONTEXT.md term) covers each Decision Request decided in the range: the Receipts of its Choices (`proposalKind` CHOICES, Redraft 1 and later) and of the Spec Proposal its Decision produced and that proposal's Redrafts, averaged over the decided requests with any. The Spec Proposal comes after the Decision, so a request decided late in the range may gain its Redrafts' cost later. Choices drafted by a chat reply are part of that reply's Receipt, not counted here.
- **Redrafts before approval** per kind of proposal (Choices, Spec, Brief Proposals, Feature Suggestions, Prompt Versions), from the APPROVE outcomes in the range (0070's `redraftsBeforeApproval`): approvals, the share approved as first drafted, and the average.
- **AI Budget** (a CONTEXT.md term): optional, monthly, in the Organization's time zone. After each Receipt is saved (a new `ReceiptsService.onRecorded` listener, inside the tracked background write, so `drain()` covers it), and when the budget is saved, this month's estimated spend is compared with 80% and 100%; a threshold crossed inserts its `AiBudgetAlert` (`ON CONFLICT DO NOTHING`) and, only if that inserted a row, notifies the Admins in the same transaction. A jump past both sends only the 100% one. Saving a budget clears the month's alerts, so a new budget is checked afresh. Without a budget nothing runs: the listener reads the budget from the Receipt settings it already loads, so no Receipt write gains a query. Nothing is ever blocked.
- **Web**: Settings → **AI usage** (`/settings/ai/usage`, also over the app as a Settings modal; `components/ai-usage.tsx`, on the 0077 kit): the range (the kit's `DateRangePicker`, its first use), headlines (estimated cost, tokens, cache hit ratio, latency, cost per decision, the budget), two charts (tokens per day, tokens by task), tables by Project and by Approved Model, Redrafts before approval, the monthly budget, and a price per Approved Model. The charts are plain HTML and CSS, no chart library (ADR 0016's bundle concern): each has a text summary, a Chart/Table switch (`SegmentedControl`), a legend, and its bars are buttons in a `toolbar` with a roving tab index (one Tab stop; the arrows, Home and End move between bars), each named by its full numbers, which a readout under the chart repeats. Colours are the `--spark-a`/`--spark-b` tokens of ADR 0008 in light and dark, with a hairline of the page between stacked parts. A range change in the modal replaces the URL (`useSettingsNavigate`), and is a full load on the page, as the Settings nav does. `TASK_LABEL` moved to `components/ai-task-labels.ts` to share it with AI models.
- **Performance**: a new benchmark scenario, `GET /settings/ai/usage` over 90 days, with Receipts written by `seedUsageReceipts` from the large Organization's own rows (one per Decision Request's Choices, Spec Proposal and Choices Redraft, about 32,000 at the large scale, and an APPROVE outcome per approved Spec Proposal). Its query budget is 8 (identity, Admin check, the Organization, then the four aggregates), checked by `perf/query-budgets.api.test.ts` on the small scale with the dashboard's numbers checked non-empty. Large scale, 60 runs, this session's machine (Intel Xeon @ 2.80 GHz, 4 cores; PostgreSQL 16.13): p50 122.8 ms, p95 147.7 ms, 8 statements; a first version carrying names through the sorts took p50 210 ms (its sorts spilled to disk). `docs/performance-baseline.json` is unchanged; the scenario is listed in `docs/performance.md`.
- **Tests**:
  - `ai-usage/ai-usage.api.test.ts` (real Postgres, `FakeAiPort`): scripted Receipts on a priced model, an unpriced one and a server-set model, in two Projects and Organization-wide, with an Eval Run and two outside the range, give the exact totals, breakdowns (every one adding up to the totals), costs, unpriced calls, latency percentiles and days; days follow the Organization's time zone; the cache hit ratio and Redrafts before approval from scripted Receipts and outcomes; cost per decision of one Decision Request through the API (Choices, a Redraft of them, the Spec Proposal and its Redraft: four calls) without an open request or an Eval Run; crossing 80% and 100% sends one Notification each to the Admin (none to a Member), also with three calls at once, a new budget re-checks, no budget sends none; without prices no cost and no Notification; prices both or neither; range validation; 403 for a Member on both routes.
  - `receipts/receipting.test.ts`: a Receipt keeps the Project given, or its Feature's, or none; `receipts.api.test.ts`: the Choices' Receipt carries the seeded Project.
  - e2e `settings-ai-usage.e2e.ts`: an Admin sees the usage, sets a price and sees a cost, sets a budget below the spend and gets one `AI_BUDGET_REACHED` (a Member none), then clears both; in light and dark, axe-clean with the charts and with a table open, the day bars are one Tab stop moved with End and the arrows with the readout following, the table view opened by keyboard has a row per day, and the task bars are named by their task; a Member gets neither the page nor the API.
- **Left open**: cached input is priced at the input price (no separate cache-read price); prices are one currency (US dollars) and apply retroactively; the budget only notifies, by design; there is no per-Project budget or export of the dashboard.
