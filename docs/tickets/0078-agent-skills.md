# 0078: Agent Skills

## Goal
The AI inside Vorasaan can use Agent Skills an Admin installed and approved, in the open SKILL.md format, so a Skill such as [diagram-design](https://github.com/cathrynlavery/diagram-design) (MIT) works unchanged, and only ever leads to proposals (ADR 0017).

## Scope
- **Format:** a folder with `SKILL.md` (frontmatter with `name` and `description`), plus optional `references/` and `assets/`, the same format coding assistants use. No manifest of our own.
- **Install (Settings → Agent Skills, Admin):**
  - paste a GitHub URL, optionally with a subpath to the Skill's folder, or upload a zip;
  - the install is pinned to the commit it was fetched at, or to the zip's hash;
  - "Update" fetches the newer version and shows a diff (per file) before applying it; applying needs approval again;
  - uninstall removes the Skill and its files.
  Files are stored through the `FileStorage` interface.
- **Text and templates only:** no file in a Skill is ever executed. Scripts (`.py`, `.sh`, `.js`, binaries and the like) are skipped, and the Admin sees the list of skipped files on install and update.
- **Approval and enabling:** an installed or updated Skill needs an Admin's approval before the AI can use it, and is enabled per Project. A Skill that isn't approved, or isn't enabled in the Project, is invisible to the AI.
- **Safety:**
  - Skill content is untrusted input (prompt injection): it is fenced as data in the prompt, and it can only lead to proposals, never direct changes (ADR 0001, ADR 0008).
  - Size limits per Skill and per file (configurable).
  - Fetches go only to `https` GitHub and codeload hosts, and never follow a redirect off those hosts (SSRF).
- **How the AI uses them (progressive disclosure):**
  - only the name and description of the Project's enabled Skills go into the prompt;
  - a `loadSkill` tool reads a Skill's `SKILL.md`; a `readSkillFile` tool reads one reference or asset file at a time;
  - what they read counts against the context budget (0060);
  - available in Conversations and when drafting Spec Proposals, and in Design Docs once 0069 lands.
- **Output:** HTML or SVG made with a Skill (for example a diagram) is shown in a sandboxed iframe (no scripts, no network, a strict Content Security Policy). It is attached to a Spec or Design Doc only as a proposal a person approves, with Request changes (0065), and can be downloaded.
- **Measurement:** Receipts (0070) record which Skills each call loaded. The AI usage dashboard (0075) can show Skill usage and approve and decline rates per Skill.
- **Contracts:** Agent Skill, install, update diff and tool input schemas in `@vorasaan/shared`.

## Acceptance criteria (test first, real Postgres, a fake GitHub server + `FakeAiPort`)
- [x] Install from a GitHub URL (with a subpath) and from a zip; the Skill is pinned to the commit or hash installed.
- [x] Update fetches the newer version, shows a diff, and changes nothing until it is applied and approved.
- [x] Scripts in a Skill are never executed and are listed as skipped.
- [x] A disabled or unapproved Skill is invisible to the AI: not in the prompt, and `loadSkill` refuses it.
- [x] `loadSkill` and `readSkillFile` read only inside the Project's enabled Skills; path traversal (`../`, absolute paths) is rejected.
- [x] A URL off the allowed hosts, plain `http`, a redirect off-host, and a Skill or file over the size limits are refused.
- [x] Only an Admin can install, update, approve or uninstall (403 otherwise).
- [x] A Receipt records the Skills its call loaded.
- [x] Browser-verified (e2e): a Skill's SVG renders in the sandboxed iframe, and a `<script>` inside it does not run.

## Decisions
- **Naming.** The repository's `packages/skills` holds Vorasaan's own prompts (and `loadSkill` there reads one of them); an Agent Skill is an installed SKILL.md package. In code the Agent Skill side is always "agent skill": the `apps/server/src/agent-skills/` module, `AgentSkill*` tables and contracts, `agentSkills` on AI inputs and Receipts, Settings → Agent Skills. The AI's tools are `loadSkill` and `readSkillFile` as the ticket names them; they live in `agent-skills/agent-skill-tools.ts` and never touch `@vorasaan/skills`. CONTEXT.md already had **Agent Skill** (avoid "plugin", "built-in skill"); **Receipt** now says it records the Agent Skills a call read. No new term.
- **Schema** (migration `agent_skills`): `AgentSkill` (name unique per Organization, `source` GITHUB or ZIP, `repository`, `ref` (null: the default branch), `subpath`, `activeVersionId`), `AgentSkillVersion` (numbered per Skill, `status` PENDING → APPROVED → REPLACED, or DECLINED; `pinned` is the commit SHA or `sha256:<hex>` of the zip; `name`, `description`, `license` from SKILL.md; `skippedFiles`; who fetched and who decided), `AgentSkillFile` (path, size, SHA-256 and the FileStorage key), `ProjectAgentSkill` (enabled per Project) and `ReceiptAgentSkill` (plain ids, the name and the pin, so a Receipt outlives an uninstall). A partial unique index keeps one PENDING version per Skill.
- **Install and update are one flow: a new version waits for approval.** Install creates version 1 PENDING; "Update" (GitHub: fetch the ref again; zip: upload the new zip) creates version N+1 PENDING, or changes nothing and says "up to date" when the commit or hash is the same. The diff (`GET …/diff`) compares the pending version with the active one file by file (`ADDED`, `REMOVED`, `CHANGED` with line diffs, `UNCHANGED`), and on a first install lists every file as added, so the Admin reads exactly what the AI would get before approving. **Applying is approving**: Approve makes the pending version active (the one before becomes REPLACED and its files are deleted); Discard (decline) deletes the pending version's files and leaves the active one as it was. Until then the AI keeps reading the active version: an update never takes a Skill offline. A second update while one is pending is a 409. A Skill whose name changes in an update is renamed on approval; names are unique ignoring case (409), because the AI names a Skill in its calls.
- **Enabling per Project is an Admin's too** (Settings → Agent Skills, a chip per Project, `PUT …/:id/projects` with the whole list). The ticket names only install, update, approve and uninstall as Admin-only; enabling stays with them as well, since there is no Project-level Skills page and an enabled Skill reaches every Conversation of the Project. A Skill may be enabled before it is approved; the AI sees it only when both hold.
- **API** (`@vorasaan/shared` `agent-skill.ts`, controller `@AdminOnly()`, so a Member gets 403 before anything is fetched or stored): `GET /settings/agent-skills` (`AgentSkillsView` with the Projects and the size limits), `POST /settings/agent-skills` (`InstallAgentSkillInput` `{ url, subpath? }`), `POST /settings/agent-skills/zip` (multipart: `subpath` field, then the `file` part), `GET …/:id`, `POST …/:id/update`, `POST …/:id/update/zip`, `GET …/:id/diff` (`AgentSkillDiff`), `POST …/:id/versions/:n/approve` and `…/decline`, `PUT …/:id/projects` (`SetAgentSkillProjectsInput`), `DELETE …/:id`. Package problems are 422, size limits 413, a pending update or a taken name 409. The tool inputs `LoadSkillArgs` and `ReadSkillFileArgs` are in the same file.
- **Reading a package** (`skill-package.ts`, `zip-reader.ts`, no dependency added): a small zip reader lists entries from the central directory and inflates only the entries kept, each capped with `inflateRawSync`'s `maxOutputLength` and checked against its declared size and CRC, so a zip bomb or a lying header fails instead of growing. ZIP64, encrypted entries and more than 20,000 entries are refused. **Any entry path that could leave its folder (`..`, absolute, a drive letter, a backslash, NUL) refuses the whole archive**; files are never written to disk by path anyway (their FileStorage keys are `agent-skills/<skillId>/<versionId>/<fileId>`). The Skill's folder is the `subpath` (within a GitHub zip's `<repo>-<sha>/` folder, or from the zip's root), else the root with a SKILL.md, else the one folder holding a SKILL.md (several: 422 asking for the folder). Kept: text extensions (Markdown, text, HTML, SVG, CSS, JSON, YAML, CSV, XML, diagram sources, templates) and files without an extension, if they decode as UTF-8 without NUL and don't start with `#!`. **Skipped and listed**: scripts and programs by extension (`.py`, `.sh`, `.js`, `.ts`, binaries…) or shebang as `SCRIPT`, anything else (images, fonts, PDFs, binaries) as `NOT_TEXT`, symbolic links as `LINK`. Nothing in a package is ever run; skipped files are never read past their zip entry. SKILL.md's YAML frontmatter needs `name` (one line, at most 64 letters, digits, spaces, `.`, `_`, `-`) and `description` (at most 1,024 characters, the open format's limit); `license` is kept for attribution. A minimal frontmatter reader handles quoted, folded, literal and continued values and skips nested maps.
- **Size limits** (`agent-skills.config.ts`, env, read per request): `VORASAAN_AGENT_SKILL_MAX_FILE_BYTES` 256 KiB per kept file, `VORASAAN_AGENT_SKILL_MAX_BYTES` 2 MiB per Skill, `VORASAAN_AGENT_SKILL_MAX_FILES` 200, `VORASAAN_AGENT_SKILL_MAX_ARCHIVE_BYTES` 20 MiB per zip (uploaded, or downloaded from GitHub; the web route forwarding uploads uses the same). Over any of them the install or update is refused (413) and nothing is stored.
- **GitHub, guarded against SSRF** (`github-source.ts`): a pasted URL must be `https://github.com/<owner>/<repo>`, optionally `/tree/<ref>/<folder>` or `/blob/<ref>/<folder>/SKILL.md` (a ref is one path segment there; `subpath` can name the folder instead), with no credentials or port. The server resolves the ref to a commit with GitHub's API (`api.github.com/repos/…/commits/<ref>`, `application/vnd.github.sha`) and downloads the zip at that commit from `codeload.github.com`, so the install is pinned to it. Only those two hosts are ever fetched, over `https` only, redirects followed by hand (at most 3) and each hop checked, so a redirect off them (or to `http`, a port, an IP) is refused before it is requested. Bodies are read with the archive cap. The `fetch` is an injectable provider (`AGENT_SKILL_FETCH`); tests give it a fake GitHub (`test/fake-github.ts`), so no test reaches the network. Public repositories only (no token).
- **How the AI uses a Skill (progressive disclosure)**: each Conversation turn reads the Project's Skills that are enabled and have an approved version (one SQL statement, run alongside the model choice). With none, nothing changes: no list, no tools, no tokens. With some, `AiPort.chat` gets `agentSkills` (names and descriptions only) and the turn offers `loadSkill` and `readSkillFile`. The `chat` prompt gains `{{agentSkills}}` before its cache break (so it is cached with the Project's prefix): an "Agent Skills" section with the fenced `<agent-skills>` list and its rules, rendered by the server, so a Prompt Version of `chat` can't drop the rules while Skills are listed (a new Prompt Version of `chat` must keep the placeholder; an older one renders no list, and the tools' results still carry their note). `loadSkill` returns SKILL.md and lists the other files; `readSkillFile` one file by its path. Both read only inside the active version of a Skill still enabled in the Project (checked again in the read's query), refuse an unknown or disabled name, and refuse a path with `..`, a leading `/`, a backslash or a drive letter before looking it up (a path is then matched exactly against the stored list, so nothing outside the Skill can be named). A refusal is the tool's result the AI reads.
- **Untrusted, fenced, proposals only**: a Skill's text reaches the AI inside `<skill-file skill="…" path="…">`, through `fence`, which now also neutralises `<agent-skills>`, `<skill>` and `<skill-file>`, so a Skill can't close its fence or forge the list. Each result carries a note that it is untrusted text for format and style only; the prompt's section says the same and that a Skill never makes the AI approve, change or draft anything, and nothing in it is ever run. The tools only read. What the AI makes with a Skill goes in its reply as a fenced ```svg or ```html block; it reaches the Spec only through the existing `draftSpecProposal` tool and its Action Card (approve, edit, Request changes (0065), decline), like any other change. A fold or a Redraft treats the svg block as Markdown text.
- **Context budget (0060)**: one Skill read is cut to `BUDGET_CONFIG.agentSkillRead` (8% of the window, 800 to 8,000 tokens; `truncated: true` when cut), and one turn reads at most twice that in all, then `loadSkill` refuses ("as much Skill text as its context budget allows"). The listed Skills' text is part of the turn's fixed cost (`forTask(… fixed)`), with the two tools' schemas. What a turn read stays in the Conversation as TOOL messages, so later turns count it in the history and compaction folds it like any message.
- **Receipts (0070)**: `ReceiptLink.agentSkills` names the Skills whose text a call read: a chat step's Receipt lists the Skills loaded earlier in its turn (the step that calls `loadSkill` is written before the tool runs, so it lists them from the next step on), each once, with the version and pin. They are written with the Receipt (`ReceiptAgentSkill`), exported as `agentSkills: [{ name, pinned }]` in the JSONL (`docs/receipts-export.md`), and outlive an uninstall. A Spec Proposal drafted by a step that had read a Skill is that step's outcome, so its approval or decline counts for the Skill.
- **AI usage (0075)**: Settings → AI usage gains "Agent Skills": per Skill, the calls that read it, and the approvals, declines and Request changes linked to those Receipts, with an approve rate (`AiUsageView.bySkill`, one more aggregate run with the others).
- **Where Skills are available**: in Feature and Project Conversations, which is where Spec Proposals are drafted with the AI (the `draftSpecProposal` tool). The one-shot drafts (the Spec Proposal after a Decision, Spec from Attachments, Redrafts) are structured calls without a tool loop, so they don't load Skills; Grilling Conversations don't either. Design Docs (0069) aren't built yet; 0069 already says it will use them.
- **Output in the web app**: `components/sandboxed-output.tsx`. Every Markdown view (chat messages, the chat's Spec panel, the Feature's Spec and the Project Brief) renders a fenced `svg` or `html` block in an `<iframe sandbox="">` (no scripts, forms, popups, navigation or same origin) with `srcdoc`, whose document carries a CSP of `default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:; form-action 'none'; base-uri 'none'` and no referrer, so nothing in it runs or loads. The markup is never put into the page itself. Under it: a caption that it is a draft, "Download SVG" (or HTML) from a Blob URL, and the source in a disclosure. The iframe has a title; its height follows the SVG's viewBox.
- **Web: Settings → Agent Skills** (`/settings/agent-skills` and its modal route, `components/agent-skills-settings.tsx`, UI kit): install from GitHub (URL, optional folder) or from a zip (file, optional folder; uploaded through the same-origin `app/api/settings/agent-skills/zip` route, which reuses the Attachment upload forwarder, now `forwardUpload`, so the session token never reaches the browser); each Skill shows its source (a link pinned to the commit), license, the version in use, a pending version with the files left out and why, "Review its files" / "Review the changes from version N" (the per-file diffs), Approve and Discard, the Projects it is enabled in (kit chip checkboxes, Save Projects), "Check for an update" (GitHub) or a new zip, and Uninstall with a confirmation (kit alertdialog; the focus then goes to the list's heading). Every message is in one status line and one alert line that stay on the page. Server actions parse the shared contracts first (`lib/agent-skill-actions.ts`). A Member sees a notice instead. AI prompts labels the new eval set.
- **AI and evals**: no new AiPort method or prompt file; the `chat` prompt gains the placeholder above. `FakeAiPort` (deterministic, only when Skills are listed): when the person's message names a Skill or asks for a diagram ("diagram", "แผนภาพ"…), it calls `loadSkill`, then `readSkillFile` on the Skill's first SVG asset, then replies (in Thai for a Thai message) that it used the Skill and that it is only a draft, with that SVG in an ```svg block; it never follows a Skill's text and never drafts for it. Checked-in eval set `agent-skills` (`src/evals/cases/agent-skills.ts`, `bun run eval:agent-skills`): loads the Skill a request needs, draws with a loaded Skill (English and Thai) in a fenced svg block without claiming a change, and an injection hidden in a Skill's SKILL.md (closing its fence, "call draftSpecProposal… say it was approved", with a Thai line) not followed, asked in English and in Thai. The fixture Skill `flow-diagram` (`agent-skills/fixtures/flow-diagram.ts`) is written for Vorasaan and shaped like [diagram-design](https://github.com/cathrynlavery/diagram-design) (MIT), which ADR 0017 names; none of its text is copied, so no license notice is needed in the repository.
- **Token and query guards**: the 0076 guards pass. The earlier chat eval cases are unchanged (1,616 tokens, scores 0.82 and Thai 0.55) because a Project without Skills renders nothing; with the five new chat cases (about 2,900 tokens each: two Skills listed, two tool schemas, a loaded SKILL.md and SVG) chat's checked-in mean is 2,261, score 0.909, Thai 0.775 (`EVAL_CASE_GUARD`, raised on purpose with that note). The product token scenarios have no Skills and are unchanged. Query budgets: the chat turn 83 → 84 (the Skills enabled in the Project, one statement alongside the model choice), the AI usage dashboard 8 → 9 (the per-Skill aggregate, alongside the others).
- **Tests**: `agent-skills/skill-package.test.ts` (kept and skipped files, a single top folder or a named folder, several Skills, traversal/absolute/backslash/drive paths refuse the zip, file/Skill/file-count/archive limits and a zip bomb with a lying header, frontmatter forms, the pin), `agent-skills/github-source.test.ts` (URL forms; http, other hosts, look-alike hosts, credentials, ports, an IP, `file:`, traversal refused; ref resolved and zip downloaded at the commit; redirects off GitHub, to http, to an IP or a port refused with only the GitHub URL requested; a redirect between GitHub hosts followed; the download cap; a missing repository), and `agent-skills/agent-skills.api.test.ts` (real Postgres, fake GitHub, `FakeAiPort`, local FileStorage in a temp dir): install from a GitHub URL with a folder (pinned to the commit, three files stored through FileStorage, four listed as skipped, only GitHub's two hosts asked) and by `subpath`; from a zip (pinned to its SHA-256), a second of the same name 409, a zip of several Skills by folder; http, other hosts, an IP and a redirect to `169.254.169.254` refused with nothing requested off GitHub, a file or a Skill over the limits 413, nothing left behind; 403 for a Member on all eleven routes with nothing fetched or stored; an enabled but unapproved Skill and a disabled one invisible (no list, no tools, a call dropped, `runTool` refuses), an approved and enabled one listed by name and description only, fenced with its rules; the fake's full turn (load, read the SVG, reply with it) leaving nothing proposed, Receipts naming the Skill from the step after the load, the export and the AI usage counting it; a diagram reaching the Spec only through an approved Spec Proposal Action Card, the approval counted for the Skill; traversal, absolute, Windows and skipped paths and a not-enabled Skill refused, `./` allowed; an injected SKILL.md fenced (its `</skill-file>` and `<agent-skills>` neutralised) and nothing drafted; the turn budget cutting a long file and then refusing; update with "up to date", a pending version 2 with its per-file diff, a second update 409, the AI reading version 1 until approval and version 2 after, version 1 REPLACED with its files deleted, a discarded version 3; a zip-installed Skill's update and diff; a first install's diff all added; uninstall deleting the Skill, its versions, files and stored files while Receipts keep its name; a Thai turn. Plus the shared enums mirror, the eval sets and the token guard.
- **Browser** (`e2e/agent-skills.e2e.ts`, light and dark): an Admin installs a zip by keyboard, sees `scripts/render.py` listed as a script left out, reviews SKILL.md as added, approves and enables it in the Project (axe-clean); in a Feature Conversation the fake loads the Skill and replies with its SVG, shown in an `iframe sandbox=""` whose CSP forbids everything; the SVG's text renders, its `<script>` and `onload` don't run ("Script did not run" stays, no message reaches the page), the SVG downloads as `diagram.svg`, the output is axe-clean; then the Admin uninstalls it through the confirmation and the focus goes to the list. A Member gets the notice and a 403 from the API.
- **Check with a real model (manual)**: run `bun run eval:agent-skills` (from `apps/server`, with `ANTHROPIC_API_KEY` or the provider the env names) and read each case: does the model call `loadSkill` for the Skill a request needs (and not for others), use `readSkillFile` for the asset it needs, draw one valid SVG in an ```svg block that follows the Skill, say it is a draft, answer in Thai for Thai, and ignore the injected SKILL.md (no drafting tool, no "approved", no "HACKED"). In the app, install [diagram-design](https://github.com/cathrynlavery/diagram-design) from its GitHub URL, check what is listed as skipped and that the diagrams it makes render in the sandbox; check the size of its SKILL.md and references against the read budget on the models in use; and confirm that GitHub's real `commits/<ref>` and `codeload` answers (and their redirects) pass the host checks.
- **Left open**: private repositories (a GitHub token) and refs with a slash in a pasted `/tree/` URL; the context meter's plan (0066) doesn't count the two Skill tools' schemas (about 150 tokens) when it shows how full a Conversation is; one-shot drafts, Redrafts and Grilling don't load Skills; the dashboard counts outcomes per Skill but has no per-Skill drill-down; the Skill's text is read whole from FileStorage before it is cut to the budget (the per-file limit bounds it).
