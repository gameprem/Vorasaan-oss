# 0072: The AI proposes better prompts

## Goal
The AI turns accumulated feedback into a proposed Prompt Version with evidence, and an Admin decides whether to use it (ADR 0015).

## Scope
- **Analysis per task:** on demand from Settings, or when a task has enough new feedback (configurable, 20 outcomes by default), the AI reads that task's Receipts and outcomes and names the patterns, for example "Choices often asked to be shorter" or "Spec Proposals often declined for missing error cases", each with the number of cases and links to them.
- **Proposal:** from the patterns, the AI proposes a new Prompt Version of the task's prompt, with its rationale.
  - Evals (0071) run on it automatically, against the active Prompt Version.
  - The proposal shows the patterns, the diff, before and after scores, and sample outputs side by side.
- **Decide (Admin):** Approve makes it the active Prompt Version; Decline takes a reason; Request changes asks for a Redraft (0065), with a new `ProposalKind` for Prompt Versions, and its evals run again. Rollback works as in 0071.
- **Never publishes by itself.** Nothing changes until an Admin approves, even if every score improves.
- **The prompt** for the analysis and the proposal lives in `packages/skills`, with eval cases including Thai feedback.

## Acceptance criteria (test first, real Postgres + `FakeAiPort`)
- [x] With 20 scripted "shorter please" outcomes on Choices, the analysis names the pattern and a Prompt Version is proposed with a rationale.
- [x] Evals run on the proposal, and its before and after scores are returned with sample outputs.
- [x] Approve makes it active; Request changes produces Redraft 2 and reruns evals; Decline stores the reason.
- [x] Without approval, every task keeps using the active Prompt Version, even when the proposal scores higher.
- [x] Only an Admin can approve, decline or request changes (403 otherwise).

## Decisions
- **Feedback Analysis** (a new CONTEXT.md term): one reading by the AI of the outcomes (0070) linked to one prompt's Receipts. A prompt's outcomes are those whose drafting Receipt or Redraft Receipt rendered it, never an Eval Run's: Request changes on Redraft 2 of some Choices is feedback on both `generate-choices` (which drafted them) and `redraft-choices` (which wrote Redraft 2). It reads the newest 200, oldest first, with the prompt's active version as written. The AI cites each pattern's cases by number; the server maps them back to their outcomes, drops unknown or repeated numbers and any pattern with fewer than 2 cases (`MIN_PATTERN_CASES`), and stores each pattern with its count and its cases by reference (outcome, Receipt, proposal, Redraft). **People's words are never copied**: the view reads them from the outcomes, so they go when retention deletes those (ADR 0015, private by default), while the pattern and its count stay. The view links each case to its proposal in the web app (`href`).
- **When it runs.** An Admin asks (`POST /settings/ai/prompts/:name/analyses`, 422 with no feedback yet, 409 while one runs: a partial unique index keeps one RUNNING analysis per prompt), or on its own once a prompt has `promptAnalysisAfter` new outcomes since its last analysis that didn't fail (Organization setting, default 20; 0 only when asked; `GET`/`PUT /settings/ai/prompt-analysis`). `ReceiptsService.onOutcome` tells `PromptProposalsService` the prompts of every new outcome. It doesn't start while an analysis of the prompt runs or one of its AI proposals waits for a decision, so a burst of feedback starts one. Analyses are background jobs like Eval Runs: an analysis left RUNNING by a stopped server is marked FAILED at the next start; `drain()` waits for analyses, the evals they start and the Receipts and outcomes all of it leaves (tests, shutdown).
- **The proposal** is an ordinary `PromptVersion`, PROPOSED, numbered next, with no writer, `analysisId` and `rationale`. The AI starts from the active version as written and must keep every placeholder the prompt is given (0071's render check, now `assertRenders`); a template that fails it, or that changes nothing, fails or ends the analysis without a version. No pattern, no proposal. Hand-written versions keep 0071's behaviour.
- **Evals run on it automatically**, against the version active then: two Eval Runs on the Approved Model of the prompt's task (`chooseModel`), with every source the prompt has (its checked-in cases, and a replay when there is one), started as whoever asked (null for one nobody asked for). `PromptVersion.evalRunId` and `baselineRunId` point at the current pair. Without an Approved Model, or without any case, none run and the proposal says why (`evalsNote`). `PromptEvalsService.begin` is `start` without a `User`.
- **Review**: `GET /settings/ai/prompts/:name/versions/:number/proposal` (`PromptProposalView`): the version, its analysis with the patterns, the diff from the version it was evaluated against, both runs, their comparison once both are done (scores per set and per case, sample outputs side by side) and `evalsNote`. 404 for a version written by hand.
- **Decide (Admin)**: Approve and Decline are 0071's routes. For an AI proposal, Approve waits for a Redraft being written (409), and Decline takes a reason (422 without; the AI learns from it). Both are recorded as outcomes of the proposal (`PROMPT_VERSION`), linked to the Receipt of the call that proposed it, so the Learning Loop's own prompts get feedback too. Rollback is 0071's.
- **Request changes** reuses 0065: a new `ProposalKind` `PROMPT_VERSION` (with `Redraft.promptVersionId`, the CHECK extended), `RedraftContent` kind `PROMPT` (template and rationale; its text, diffed, is the template), routes `POST /prompt-versions/:id/request-changes`, `GET /prompt-versions/:id/redrafts[/diff]` (Admins only; 422 for a version written by hand, 409 once decided). The AI is given the current Redraft, its rationale, the patterns, the active version and the earlier feedback; a Redraft that wouldn't render is a 502 that changes nothing. **A proposal the AI made holds its latest Redraft while PROPOSED**, like every AI proposal: it is the one exception to "a Prompt Version never changes", and only until it is decided. Its name (`v<n>@<hash>`) follows its template (the name cache is keyed by template too). When a Redraft is READY, `PromptProposalsService` (a Redraft listener) runs its evals again, as whoever asked.
- **Never publishes by itself.** Nothing but an Admin's Approve writes a `PromptActivation`; scores are only shown.
- **AI**: three `AiPort` methods and prompts in `packages/skills`: `analyze-feedback` (`analyzeFeedback`), `propose-prompt-version` (`proposePromptVersion`), `redraft-prompt-version` (`redraftPromptVersion`), a new Settings task `PROMPT_PROPOSALS` ("Prompt proposals" in AI models) with `VORASAAN_MODEL_*` overrides. Receipts: the analysis outputs `PROMPT_ANALYSIS`, the proposal `PROMPT_VERSION` (proposal `PROMPT_VERSION`, Redraft 1). A template is data in a `<template>` block where only `<template>` itself is neutralised (`fenceTemplate`), so the AI gives it back as written; people's words are fenced as usual. The markers a version must keep (`{{>language}}`, `{{cacheBreak}}`) are given as values, never written in the prompts, so they are never expanded. `FakeAiPort`: patterns from English and Thai keywords (shorter, error cases, Thai) and hand edits, at least 2 cases each; the proposal appends one `- Learned from feedback: <pattern>.` line per pattern; a Redraft appends `- Changed as asked: <feedback>`.
- **Evals**: `bun run eval:prompt-proposals` and the checked-in set `prompt-proposals` (`src/evals/cases/prompt-proposals.ts`): the analysis in English, Thai and mixed Thai-English with an injection, a proposal for an English and a Thai Admin, and a Redraft from Thai feedback with an injection, checked for the cases cited, placeholders kept and injections not followed.
- **Web**: Settings → AI prompts shows each prompt's new feedback and the setting "The AI reads a prompt's feedback after N new outcomes". A prompt's page gains **Feedback**: the new outcomes, "Analyze feedback now", and each analysis with its patterns, counts and cases (linked to their proposals), and the version it proposed; the page refreshes while one runs. An AI proposal shows "Proposed by the AI" and its rationale in Versions, and "Review the proposal" opens `/settings/ai/prompts/[name]/proposals/[number]` (`components/prompt-proposal.tsx`, also over the app as a Settings modal): the patterns, the diff, the scores before and after with the comparison, and Decide: Approve, Decline with a required reason, and Request changes with the Redrafts (0065's components, `REDRAFT_SLUG.PROMPT_VERSION`). The diff rows now use body text on their tint (the green on green was below AA contrast).
- **Tests**:
  - `prompt-versions/prompt-proposals.api.test.ts` (real Postgres, `FakeAiPort`): 20 "shorter please" outcomes on Choices name the pattern with its 20 cases and links, and propose v1 with a rationale; the analysis and the proposal leave their Receipts; people's words aren't stored in an analysis and go with retention while its pattern stays; Thai feedback, and a pattern needs two cases; no pattern proposes nothing; no feedback is a 422, a failed call fails the analysis; evals run on the proposal and the default with scores and sample outputs side by side, or say why not without an Approved Model; Approve makes it active (and the next call uses it), recorded as an outcome, and rollback works; Request changes writes Redraft 2, reruns its evals, and Approve applies it; a failed Redraft changes nothing; Decline takes and stores a reason; a hand-written version has no proposal and isn't redrafted; without approval every task keeps the active version though the proposal scores higher; 20 new outcomes start an analysis on its own, once; 403 for a Member on every route, with nothing called or stored.
  - `evals/eval-sets.test.ts`, `ai/language.test.ts`, `receipts/receipting.test.ts` cover the three new tasks.
  - e2e `prompt-proposals.e2e.ts`: feedback through Request changes, an Admin analyses it, sees the pattern and its cases, reviews the proposal (diff, scores before and after, samples; axe-clean), asks for a Redraft, sees its evals rerun, approves it and rolls back; a Member gets neither the page nor the API.
- **Checked by hand, not in automated tests**: the three prompts on a real model (`bun run eval:prompt-proposals`).
- **Left open**: a Feedback Analysis reads one prompt at a time and isn't streamed; the proposal page doesn't show a Redraft's own patterns (the analysis's stay the evidence); evals of a proposal run on the task's model only (others by hand, as in 0071).
