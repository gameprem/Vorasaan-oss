# 0080: Gemini as an AI Provider

## Goal
An Admin connects the Gemini API with only a key from Google AI Studio, picks Approved Models from Gemini's model list, and gets the right Context Window and Gemini's own prompt caching without typing them (ADR 0010, ADR 0012), the way OpenRouter works (0064).

## Scope
- **A new kind:** `GEMINI` in `AiProvider` (`packages/shared/src/ai-settings.ts`), next to `ANTHROPIC`, `OPENAI`, `OPENAI_COMPATIBLE` and `OPENROUTER`. Its label is "Gemini API"; its default name "Gemini".
  - The Admin enters only a name and the key, encrypted with `VORASAAN_SECRET_KEY` like every provider key. The base URL is fixed (`https://generativelanguage.googleapis.com/v1beta`) and not editable; a `baseUrl` for it is a 422, as for OpenRouter.
- **Calls:** through the AI SDK's Google provider (`@ai-sdk/google`), the version Mastra bundles, so no new dependency; the key in the `x-goog-api-key` header only.
- **Model list:** adding an Approved Model on a Gemini provider loads Gemini's `GET /models` (read with the provider's key) into the picker, only the models that generate text, searchable by name and id.
  - Picking a model prefills its Context Window from the list's `inputTokenLimit` (0060). The Admin can still change it.
  - If the list can't be loaded, the Admin types the model id; the window falls back to the known-model table, else the default.
  - The setup wizard lists the models too, for the key typed there.
- **Prompt caching (0061):** Gemini caches a repeated prefix by itself (implicit caching), so it gets the stable-first prompt as it is, with no marks. Cached tokens from Gemini's usage are logged and recorded on Receipts (0070) and in the AI usage dashboard (0075).
- **Structured output and tool calls** work for every AiPort task and the chat tools, within the JSON schema subset Gemini accepts.
- **Token counting:** the 0059 estimate.
- **Embeddings (ADR 0007):** decide whether Gemini embeddings fit the current EMBEDDINGS design.
- **Test connection** works for a Gemini Approved Model, and a key echoed in an error is masked.

## Acceptance criteria (test first, real Postgres, a fake Gemini API)
- [x] A Gemini provider is created with a name and a key only; a base URL is refused.
- [x] The model list is loaded with the provider's key and searchable, and a picked model's Context Window is prefilled from `inputTokenLimit`; a list that can't be loaded falls back to typing the id.
- [x] A task and a chat on a Gemini model send the prompt unmarked, with structured output and tools in the schema subset Gemini accepts.
- [x] Cached tokens from Gemini's usage are logged and reach the Receipt.
- [x] Test connection succeeds against the fake API and reports its error otherwise, with the key masked.
- [x] The key never appears in an API response, a URL or a log line.

## Decisions
- **Schema** (migration `20261013120000_gemini_provider`): `GEMINI` added to the `IntegrationProvider` enum, in a migration of its own (a new enum value can't be used in the transaction that adds it). Its key is encrypted with `VORASAAN_SECRET_KEY` in `OrgIntegration.secretEncrypted`, like every provider's.
- **Naming.** The kind is `GEMINI` (the product an Admin gets a key for in Google AI Studio), not `GOOGLE`: Vertex AI is a different API with different auth, and stays out of scope. Mastra's own id prefix for it is `google/`, so env models and Receipts map `google/` to `GEMINI`.
- **API contract** (`@vorasaan/shared`):
  - `AiProvider` gained `GEMINI` (label "Gemini API" in the web app, default name "Gemini", no default model). `CreateAiProviderInput` and the setup's `AiSettingsInput` take `{ kind/provider: 'GEMINI', name, apiKey }`.
  - A `baseUrl` for Gemini is a **422** everywhere, as for OpenRouter: create, `PATCH`, `POST /setup/test-ai` and `POST /setup` (before anything is written).
  - `OpenRouterModelView`/`OpenRouterModelsView` became `ProviderModelView`/`ProviderModelsView` (same shape, `{ id, name, contextWindow }` and `error`), since both providers use them. `GET /settings/ai/providers/:id/models` (Admin) answers for an OpenRouter or a Gemini provider; 422 for another kind, 404 for an unknown one, 403 for a member. A list that can't be loaded is a 200 with `models: []` and `error`.
  - `POST /setup/gemini-models` `{ apiKey }` (Setup Token; 400 without a key) returns the same for the wizard. Unlike OpenRouter's, Gemini's list needs a key; the key travels in the body, is used for that one request and is not stored.
- **Calls go through Mastra's bundled Google provider** (`@ai-sdk/google` 3.0.101, bundled inside `@mastra/core` 1.72.0 and built for the AI SDK version Mastra runs), as `{ id: 'google/<model id>', apiKey }`. **No new dependency:** installing `@ai-sdk/google` ourselves would add a second copy that Mastra's model router doesn't use for `google/` ids, and could drift from Mastra's AI SDK version; the pinned `@mastra/core` pins the provider. The provider calls `models/<id>:streamGenerateContent?alt=sse` with the key in the `x-goog-api-key` header, never in the URL. As with OpenRouter, the config has no `url`, or Mastra would switch to its generic OpenAI-compatible route.
- **Base URL.** Fixed at `https://generativelanguage.googleapis.com/v1beta`. `GOOGLE_BASE_URL` (Mastra's own `<PROVIDER>_BASE_URL` variable for this provider, so the calls and the model list can't disagree) overrides it for tests, only when it is an http(s) URL; an Admin can never set it. The list fetch uses `redirect: 'error'` and a 10-second timeout. No input from a request reaches the URL, so neither the list nor the calls are an SSRF path.
- **Model list and window.** `GET /models?pageSize=1000` with the key in `x-goog-api-key`, following `nextPageToken` for at most 5 pages. Only models whose `supportedGenerationMethods` include `generateContent` are listed (embedding and other models are left out); the `models/` prefix is dropped from the id; the name is `displayName`, else the id. Sorted in code by name, then id (`localeCompare(…, 'en')`), never by the provider's order. The Context Window is `inputTokenLimit`, the most one request may hold (a value outside 4,096 to 10,000,000 is left for the Admin); not `outputTokenLimit`, since 0060's budgets already keep a share of the window for the reply. The server prefills the same way when no window is given (create, a changed model id, setup): the list's limit read with the provider's key, else the known-model table, else the default. The table gained `gemini-1.5-pro` (2,097,152) and `gemini-` (1,048,576). The 0060 backfill migration is not touched: it ran once, and the table only prefills new models.
- **List errors never carry the provider's body**, which may echo the key: a 400, 401 or 403 says "The Gemini API refused the key (N) when listing its models", any other status "The Gemini API answered N for its model list", and a network error its message with the key masked.
- **Setup wizard.** Gemini is a fifth provider tile. Its list needs the key, so the provider step shows **Load Gemini models** once a key is typed; it loads the list with that key, and changing the key or the provider hides the list until it is loaded again. With no list, the model id is typed (the server prefills the window either way).
- **Prompt caching (0061).** Gemini caches a repeated prefix by itself (implicit caching, on by default on current models, with a minimum prefix length per model) and gives the discount on cache hits. Vorasaan's prompts are already stable-first, with the Brief, Guidelines and Spec before retrieved context and history, so Gemini gets the plain text, as OpenAI does: `cacheMarkOf('google/…')` is null and nothing is marked. **Explicit caching (`cachedContent`) is not used:** it needs a cache resource created per stable prefix through a separate API, with a TTL, storage billed by the hour, a minimum size and create/expire bookkeeping per Organization and model, for a prefix that changes with every Spec Version; implicit caching already covers repeats within minutes, which is how Conversations and redrafts run.
- **Cached tokens.** The provider reports Gemini's `usageMetadata.cachedContentTokenCount` as `cachedInputTokens`, so `[AiUsage]` logs it as the cache read and Receipts and the AI usage dashboard (0070, 0075) record it with no new parsing. Gemini reports no cache writes: the log shows `cache write ?` and the Receipt stores null.
- **Structured output.** The provider sends `responseMimeType: application/json` and a `responseSchema` converted to Gemini's OpenAPI subset; Mastra's schema-compat layer for Google models turns constraints Gemini doesn't take (such as a number's minimum on a tool argument, or a string's length) into the field's description. A test sends every AiPort task schema and every chat and Agent Skill tool to the stand-in and checks that only fields of Gemini's Schema object reach it. The answer is still validated with the task's Zod schema, retried once on a mismatch (`generateStructured`), as for every provider.
- **Tool calls.** Tools reach Gemini as `functionDeclarations` with `functionCallingConfig: AUTO`, and a `functionCall` comes back as the chat's tool call. Gemini 3 models refuse a replayed function call without a thought signature; Vorasaan stores tool calls without provider metadata, so the provider sends Gemini's documented `skip_thought_signature_validator` placeholder for such a call (tested) instead of failing with a 400.
- **Too long.** Gemini's "The input token count (…) exceeds the maximum number of tokens allowed (…)" now counts as a too-long request, so a Conversation compacts and retries once (0060).
- **Token counting** is the 0059 estimate: `countTokens` uses Anthropic's API only for the `ANTHROPIC` provider. Gemini has a free `countTokens` call, but it would add a request before every turn; the estimate is what 0060's budgets were tuned with.
- **Env models.** `VORASAAN_MODEL_<TASK>=google/<model id>` uses the oldest connected Gemini provider's key, else Mastra reads `GOOGLE_API_KEY` or `GOOGLE_GENERATIVE_AI_API_KEY`. The eval scripts take the same form.
- **Keys in logs.** The `RedactingLogger` from 0064 masks the call's key in Mastra's log lines for Gemini too (Gemini's error for a bad key does not echo it, but a stand-in that does is tested). Test connection masks it in its result. No key is ever in a URL, a response or a Receipt.
- **Embeddings (ADR 0007): no code.** EMBEDDINGS is an OpenAI-compatible endpoint (URL, key, model), and the Gemini API serves one at `https://generativelanguage.googleapis.com/v1beta/openai` (`POST /embeddings` with the key as the bearer token), so an Admin can already use `gemini-embedding-001` there; the README says how. Its 3,072 dimensions fit the design: the vector column has no fixed dimension and each chunk records its model and dimension. They are over pgvector's 2,000-dimension HNSW limit, so search ranks those vectors exactly, as `ContentChunkRepository` already does above the limit; fine for a Project's scope, slower on very large ones. A native Gemini embeddings adapter would add a second EmbeddingPort and a new settings shape for the same vectors, so it was not built. Not checked against Google here (no key).
- **Web.** Gemini is a fifth kind in Settings → AI models and the setup wizard (name and key only, no URL field; the tiles are 3 and 5 to a row). The searchable picker is now `ProviderModelPicker` (formerly `OpenRouterModelPicker`), named by provider ("Search Gemini models", "Gemini models") and with the provider's own example id in its fallback message; `listOpenRouterModels` became `listProviderModels`.
- **Tests.** `gemini.test.ts` (MastraAiPort against a local stand-in for the Gemini API, `src/test/fake-gemini.ts`: a task's prompt unmarked with structured output, cached tokens in the log and on the usage a Receipt gets, a chat's system instruction and turns, tool declarations and a tool call back, the thought-signature placeholder on a replayed call, every task schema and tool within Gemini's Schema fields, the key only in the header, the estimate for counting, Test connection ok and failing with the key masked in Mastra's log, the model list across pages and filtered, its failures without the key, the base URL rules), `gemini-settings.api.test.ts` (create with a key only, 422 for a URL on create and `PATCH`, the list read with the stored key and the window prefill, a changed model id re-prefilled, the fallback, a refused key, 403/404/422 on the list, the choice of model, Test connection through the API with the echoed key masked, no key in any response, the env model, setup's list and setup with Gemini and its 422), `prompt-cache.test.ts` (no mark for `google/…`), `token-count.test.ts` (Gemini's too-long message), the picker's search (`provider-model-picker.test.ts`) and `e2e/gemini-settings.e2e.ts` (connect, load the list with the key, search and pick by keyboard, the window shows "1M tokens", the fallback message, axe-clean in light and dark; it removes the model and the provider it added), against a fake Gemini API on `E2E_FAKE_GEMINI_PORT` (4017).
- **Manual check (not done here: no Gemini key in this environment).**
  1. Get a key at https://aistudio.google.com/apikey. Settings → AI models → Connect a provider → **Gemini API**, with a name and the key. Add a model: Gemini's list loads; search for a Pro or Flash model, pick it, and see its Context Window filled in (about 1M tokens). Press **Test** on the model: "Connected to gemini-…". A wrong key gives Gemini's own error, without the key in it.
  2. On a Project with a Brief of a few paragraphs and a Feature with a Spec, open a Feature Conversation on that model and send two messages within a few minutes. The server log shows `[AiUsage] chat: input N (cache read 0, cache write ?)` and then, once the prefix is long enough for the model's implicit caching minimum, `cache read M` with M > 0; Settings → AI usage shows the cache hits.
  3. Ask it to propose a Spec change: an Action Card appears (a tool call), and Approve works.
  4. Raise a Decision Request on that model (Settings → AI models → model per task → Choices): the Choices come back (structured output).
  5. With the key in the environment, run the evals on Gemini, e.g. `cd apps/server && GOOGLE_GENERATIVE_AI_API_KEY=… VORASAAN_MODEL=google/gemini-2.5-flash bun run eval:choices` (also `eval:conversation`, `eval:redrafts`, `eval:grilling`, `eval:design-docs` and the others). `VORASAAN_MODEL` applies while the database has no Approved Model; otherwise set `VORASAAN_MODEL_<TASK>`, e.g. `VORASAAN_MODEL_GENERATE_CHOICES=google/gemini-2.5-flash`. In the app, Settings → AI prompts runs a Prompt Version's eval on a Gemini Approved Model.
  6. Optionally, embeddings (an Admin's API call; there is no settings page for them yet): `PUT /settings/embeddings` with `{ "baseUrl": "https://generativelanguage.googleapis.com/v1beta/openai", "model": "gemini-embedding-001", "apiKey": "…" }`, then `POST /settings/embeddings/reindex`, and check that a Conversation's answer cites a Spec section asked about in other words.
- **Left open.** Thought signatures are not stored with tool calls (the placeholder keeps Gemini 3 working, and Gemini warns it may reason a little worse on that step). Explicit context caching and Gemini's `countTokens` are not used. The list is fetched on each form open and each window prefill, with no cache, as for OpenRouter. Vertex AI and Gemini's own embeddings endpoint are not supported.
