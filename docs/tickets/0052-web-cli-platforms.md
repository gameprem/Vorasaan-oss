# 0052: Web and CLI: Platforms and Coverage

## Goal
People pick Platforms, see Coverage at a glance, and fix the gaps from where they work.

## Scope
- **Web:**
  - Settings modal → Platforms: edit the Organization template.
  - Project → Platforms: add, rename, reorder or remove Platforms; map Team Roles; switch checks on or off.
  - A Feature header shows one chip per target Platform: jade when covered, saffron when missing, with the reason on hover or tap.
  - Project Coverage view: a Feature × Platform matrix, filterable to "missing only" and by reason (for example "missing QA"), so QA can see which Platforms still need test cases.
  - In chat, the AI can propose "Add a Flutter section" as an Action Card (0043).
- **CLI:**
  - The Features tab shows each Feature's Platform chips.
  - `vorasaan raise` suggests the Platform from the files changed in the repository, for example `lib/**/*.dart` → Flutter. The suggestion is only a hint.

## Acceptance criteria
- [x] Browser-verified: a Flutter Platform is added to a Project, a Feature targets it, and it shows as missing. A Spec section is added, and it shows as covered.
- [x] The matrix is readable at 375px wide: it scrolls inside its own container, and the page doesn't scroll sideways.

## Decisions
- **Reconciled with the app shell (0045, 0008, ADR 0016)**:
  - *Settings modal → Platforms* is a new Settings section, `/settings/platforms` (with its intercepted modal route), after Feature Guidelines. Admins edit the Platform template (`PUT /settings/platform-template`); every other member reads it, with a note that a Project's POs change their own list. It says when the built-in template still applies.
  - *Project → Platforms* and the *Project Coverage view* are two new tabs of the Project page, **Platforms** and **Coverage** (the Project page's tabs are its sections; the Sidebar lists Projects and Features, not views). The Platforms tab edits the Project's list for its POs and Admins (`canEdit` from `GET /projects/:id/platforms`) and shows it read-only to everyone else.
  - Both lists use one editor (`components/platforms-editor.tsx`), saved whole like the Feature Guidelines editor: per Platform its name, its Team Roles (the kit's chip checkboxes) and its four Coverage checks (kit checkboxes with a line on what each means), with Up, Down and Remove, and "Add a Platform". After a move or a removal the focus goes to the same row's button or the next row's Remove; the status line ("Flutter removed. Unsaved changes", "Saved.") sits outside the list, so removing a row never takes its message with it. A refused save (the 409 `PlatformsInUse`, whose message names the Features) shows as an alert. Server actions parse the shared Zod contracts first (`lib/platform-actions.ts`). The keys of the rows rendered first come from the id or the position, never a counter, so the server's and the browser's `data-row` agree.
- **Feature header chips** (`components/coverage-chips.tsx`): the Feature page reads `GET /features/:id/coverage` when the Feature targets any Platform, and shows one chip per target, a kit Button named "Flutter: missing" or "Back-End: covered". The tint is jade or saffron, with a check or "!" mark in that colour; the text stays the foreground colour, because saffron and jade text on their washes are under 4.5:1. The reason shows **on hover or focus** (a kit Tooltip) and **on a press or tap** (a popover dialog), since a tooltip never opens on a phone. The popover lists each gap in `coverageGapText`'s words and what can be done: links to the open Blockers that name the Platform; for "No Spec section", to the Feature's PO or an Admin, "Ask the AI to add a Flutter section"; for missing acceptance criteria, to them too, **Draft acceptance criteria** (`POST /features/:id/coverage/acceptance-criteria`, 0051), whose result ("…drafted as a Spec Proposal. Review it") is announced from a status line outside the popover. Without Coverage (an error) the header falls back to the plain names.
- **Coverage matrix** (`components/coverage-matrix.tsx`, the Coverage tab): `GET /projects/:id/coverage` as a table, Features as rows (with their Team) and the Project's Platforms as columns; each cell is "Covered", "Missing" with its reasons, or "Not targeted". Above it, the Platforms no Feature covers. Filters: a kit Switch "Missing only" and a kit Select "Reason" (Any reason, No Spec section, Nobody to ask, Open Blockers, Missing QA); a row stays when one of its cells is missing (for that reason), so QA picks "Missing QA". The filters are kept in the address (`?tab=coverage&missing=1&reason=QA_READY`) to share or reload. The table sits in a focusable, labelled `section` that scrolls sideways on its own (its Feature column sticky), so at 375px the page itself never scrolls sideways. Rows are in the server's order; nothing in the tests depends on how titles sort.
- **In chat** (the Action Card of 0043): the AI can now see the gap. A Feature Conversation's turn reads its target Platforms (with "Spec section" on) whose section the latest Spec Version lacks (`CoverageService.missingSectionsOfLatest`, two queries run alongside the foundation) and passes them to `AiPort.chat` as `missingSections`. The `chat` prompt gains `{{missingSections}}`: a "Missing Platform sections" block with a fenced `<platforms>` list and one rule (when the person asks or agrees, offer to add a `## <Platform>` section as a Spec Proposal, from what the Spec, the Decisions and the context say, or else one open question; never invent requirements). It renders **nothing** when no section is missing, so other Conversations cost no extra tokens; a new Prompt Version of `chat` must keep the placeholder. The Spec Proposal itself is the existing `draftSpecProposal` tool and its Action Card; no new tool. The FakeAiPort's reply adds "The Spec has no section for Flutter yet; I can propose adding one." The chip's "Ask the AI to add a Flutter section" opens `/conversations/new?feature=…&section=Flutter`, where "Add a Flutter section to the Spec" is the first chip above the composer (it only fills the composer; the name is checked with `PlatformName`).
- **Budgets**: the chat turn's query budget goes from 81 to 83 on purpose (the two reads above; measured 79 → 81 on the small large-Organization scale). The Feature page now also reads `GET /features/:id/coverage`, already measured by its own scenario (budget 7); the "Feature page (5 requests)" scenario keeps its five reads, so the 0073/0074 baselines stay comparable. The 0076 token guards pass unchanged: the eval cases have no missing sections, and in the token scenarios the block is small.
- **CLI**:
  - The Features tab reads `GET /projects/:id/coverage` once per Project in the list (alongside, after `GET /features`; a failure only drops that Project's chips) and shows each Feature's target Platforms after its line: `✓ Back-End` in green, `! Flutter` in yellow, the mark saying it without colour. The full help (`?`) explains them.
  - `vorasaan raise` prints a hint after the Feature is picked: `Hint: 2 changed files (lib/main.dart, …) suggest the Flutter Platform. If this is about Flutter, name it in the title so Coverage counts it there.` (plus "This Feature doesn't target Flutter." when it doesn't). Changed files are `git diff HEAD --name-only` and untracked files git doesn't ignore; nothing is read or sent. Rules (`commands/platform-hint.ts`): a directory first (`ios/`, `android/` → Mobile; `web/`, `components/` → Front-End; `server/`, `api/`, `migrations/` → Back-End), else the extension (`.dart`/`pubspec.yaml` → Flutter; `.swift`, `.kt` → Mobile; `.tsx`, `.css` → Front-End; `.go`, `.py`, `.sql` → Back-End). A match is named as the Feature's own target is named ("Flutter app" if that is its name). It is only a hint: it fills in nothing, and naming the Platform in the title is what Coverage's "No open Blockers" check reads. The TUI's raise form is unchanged.
- **Glossary**: CONTEXT.md gains **Coverage matrix**.
- A small fix met on the way: the Decision speed panel's hint text (`text-fg-faint`, 2.9:1) failed axe on the Project page; it is `text-fg-soft` now.
- **Tests**: server, real Postgres and `FakeAiPort` (`coverage/coverage-chat.api.test.ts`): a Feature Conversation gets Flutter as missing and the prompt fences it, a Project Conversation or a switched-off check gets none, and "Add a Flutter section" becomes a Spec Proposal Action Card whose approval covers the section (receipts and indexing drained). CLI: `platform-hint.test.ts` (rules, naming, the hint's words, changed and untracked files in a real git repository, a failing server) and the Features tab's chips (`App.test.tsx`). Browser (`e2e/coverage.e2e.ts`, axe-clean): the acceptance criterion end to end (Project → Platforms adds Flutter for Mobile with two checks off, the Feature targets it and its chip says missing with "No Spec section", the chip's chat link proposes the section, approving the card makes the chip "covered"); the matrix at 375px in light and dark (scrolls inside its region by keyboard, the page doesn't, filters to Missing QA, kept on reload); Settings → Platforms in light and dark (keyboard moves and removal keep focus and the status line; a Member only reads). Each spec puts the seeded Project's Platforms and targets back. `platforms.e2e.ts` (0050) now reads the header as chips.
- **Not here**: per-Platform Design Docs read the same Coverage in 0069; the TUI's raise form doesn't show the Platform hint (the ticket names `vorasaan raise`).
