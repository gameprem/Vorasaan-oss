# 0069: Design Docs per Platform

## Goal
Each target Platform of a Feature gets an approved Design Doc, drafted by the AI from the approved Spec, so every team builds from the same settled "what" (ADR 0014).

## Scope
- **When:** once a Feature's Spec is approved and a target Platform's Coverage is complete (0051), the AI drafts that Platform's Design Doc. The QA Design Doc is drafted once every target Platform is covered.
- **What, per template:**
  - **Back-End:** API contract, data model, sequences, error cases.
  - **Front-End:** screens and states, API calls, validation.
  - **Mobile:** as Front-End, plus offline and push.
  - **QA:** a test plan and test cases, each traced to an acceptance criterion in the Spec.

  These are built-in templates; a Project can edit them. A Platform added later (for example Flutter) starts from the template it names.
- **Approval:** a Tech Lead or a Role Owner of the Platform's Team Roles approves, declines or requests changes (0065). Others get a 403.
- **Versions:** approved Design Docs are Markdown (ADR 0002), versioned with diffs and revert like Specs (0020), each version naming the Spec Version it follows.
- **The Spec stays the source of truth:** when a new Spec Version changes what a Design Doc covers, that Design Doc is marked stale and the AI proposes an update. A Design Doc never changes the Spec.
- **Questions:** a question found while designing is raised as a Decision Request on the Feature.
- **Elsewhere:** `vorasaan run` hands over the approved Design Doc of the developer's Platform, and the Decision Graph (0067) shows Design Docs as a sub-lane. The AI can use the Project's enabled Agent Skills (0078) while drafting, for example for a diagram.

## Acceptance criteria (test first, real Postgres + `FakeAiPort`)
- [x] No draft while the Spec has a Spec Proposal awaiting approval or the Platform's Coverage is missing; a draft once both hold.
- [x] Approve creates version 1; Request changes produces a Redraft; a later approved change shows a diff.
- [x] A new Spec Version that changes the Back-End section marks the Back-End Design Doc stale, not the Front-End one, and the AI proposes an update.
- [x] Only the Platform's Tech Lead or Role Owners can approve; others get a 403.
- [x] A question the AI finds while drafting becomes a Decision Request.

## Decisions
- **Data** (migration `design_docs`):
  - `DesignDoc`: one per Feature and target Platform (`platformId`), and one QA Design Doc per Feature (`platformId` null); a unique index on `(featureId, platformId)` for Platforms and a partial unique index for QA, both in the migration since Prisma's unique would allow many nulls. It is created when it is first drafted, keeps the template it started from (`template`), and `draftingAt` / `draftError` for the draft in progress or the last failure. A Platform no longer targeted keeps its rows (and gets them back if targeted again) but is not listed.
  - `DesignDocVersion`: immutable, numbered per Design Doc, Markdown (ADR 0002), `source` `AI_DRAFT` or `REVERT`, and `specVersionId`: **the Spec Version it follows**.
  - `DesignDocProposal`: the AI's draft, `reason` `FIRST_DRAFT` or `SPEC_CHANGED`, the Spec Version it was drafted from, the version it updates, `status` `PENDING` / `APPROVED` / `DECLINED` / `SUPERSEDED`, who reviewed it, the decline reason and the model that drafted it (0054's columns). A partial unique index keeps **one PENDING proposal per Design Doc**.
  - `DesignTemplate` (`projectId`, `kind`, Markdown): a Project's own template; none means the built-in one. `Platform.designTemplate` and `OrgPlatformTemplate.designTemplate` (`DesignTemplateKind`, nullable): the template a Platform names; **null means chosen from its Team Roles** (`platformDesignTemplate`: MOBILE → Mobile, FRONTEND or DESIGNER → Front-End, anything else → Back-End). So existing Projects and the built-in Platform template need no data change, and Flutter can name Mobile.
  - `DecisionRequest.designDocId` (set null on delete): the Design Doc whose draft raised a question. Redrafts reuse 0065's table: `ProposalKind` `DESIGN_DOC_PROPOSAL`, `Redraft.designDocProposalId`, the CHECK extended. `ReceiptOutputKind` `DESIGN_DOC_PROPOSAL`; a new Settings task `DESIGN_DOCS` ("Design Docs" in AI models).
- **Templates** (`BUILT_IN_DESIGN_TEMPLATES` in `@vorasaan/shared`): Back-End (API contract, Data model, Sequences, Error cases), Front-End (Screens and states, API calls, Validation), Mobile (Front-End's plus Offline, Push notifications), QA (Test plan, Test cases "traced to one acceptance criterion"), each with Open questions. `GET /projects/:id/design-templates` (everyone in the Organization), `PUT` and `DELETE /projects/:id/design-templates/:kind` (the Project's POs and Admins, as for its Platforms). A draft uses the template as it is when it is drafted. QA is not a Platform's template (400).
- **What a Design Doc covers, and stale** (`designDocScope` / `designDocAffected` in `@vorasaan/shared`): a Platform's Design Doc covers the Spec without the `##` sections of the Feature's other target Platforms (its own section and every general one); QA's covers the whole Spec. Whitespace changes don't count. **Stale is computed on read, never stored**: the latest Spec Version differs from the one the latest version follows in what it covers. So a new Spec Version that changes only the Back-End section makes the Back-End Design Doc stale and not the Front-End one (QA's, which covers everything, too).
- **When the AI drafts** (`DesignDocsService.sync`, in the background, one at a time per Feature, drained in tests): only from a settled Spec, i.e. a Spec Version exists, no Spec Proposal on it awaits approval (a stale one, based on an older version, doesn't count, since it can never be approved), and the Platform is covered (0051's rules, computed the same way); QA once every target Platform is covered (none targeted: it waits). A first draft when it has no version and no pending proposal; an update (`SPEC_CHANGED`) when it is stale. A pending proposal drafted from an older Spec is **superseded** when the Spec changed what it covers, else it simply follows the latest Spec Version. A Design Doc declined for the latest Spec Version isn't drafted again on its own.
  - **Triggers**: the services that change what a draft depends on tell `SpecChanges` (a small global module, so the Spec, Org and Platforms modules don't import Design Docs) after they commit: a new Spec Version (approved, written by hand, reverted), a declined Spec Proposal, a Feature's targets changed, a Project's Platform list saved. Coverage that becomes complete by other means (someone joins the Team, a Blocker is decided) shows the Design Doc **READY**, and its approvers can ask for it (`POST /features/:id/design-docs/:key/draft`, which answers at once with DRAFTING); the same button retries a failed draft or redrafts a declined one.
  - A draft claims the Design Doc (`draftingAt`, abandoned after 10 minutes), calls the AI outside any transaction, and writes the proposal only if the Spec, the pending proposal and the latest version are still as they were; otherwise it drops it and syncs again from what is current. A failure is kept as `draftError` (redacted, 300 characters).
- **Who approves** (`designDocApprovers`): for each of the Design Doc's Team Roles (Tech Lead, and the Platform's, or QA for QA's), the Feature's Role Owners holding it, or, when the Feature has no Role Owner of that role, the Team's members holding it (as 0016 chooses Recipients). **Admins are not approvers for being Admins**: the ticket says others get a 403, and an Admin who should approve holds the role. Approve, decline, Request changes, revert and asking for a draft are theirs; everyone else in the Organization reads (outside it: 404).
- **Approval** (`POST /design-doc-proposals/:id/approve` with an optional `{ redraft }`, `…/decline` with an optional `{ reason }`): Approve writes the next version following the proposal's Spec Version, which must still be the latest (else 409: an update is drafted from the new Spec), applies the current Redraft only, and waits for one being written (0065's guard). Outcomes go to the drafting Receipt (0070), so Feedback Analysis (0072) reads Design Docs too and links each case to its Design Doc.
- **Versions** (0020): `GET /features/:id/design-docs/:key` (the Design Doc, every version newest first, the pending proposal with both sides of its diff), `…/diff?from=&to=` (line diff, `from=0` an empty one), `…/versions/:n/revert` (`{ baseVersion }`): the restored version follows the Spec Version the restored one followed, so a revert past a Spec change is stale at once and the AI proposes the update.
- **Questions found while designing**: the draft returns at most 5 `questions` (what the design needs that the Spec and the Decisions leave open). Each becomes a **DRAFT Question on the Feature, plain text, to the PO**, raised by one of the Design Doc's Role Owners (the Platform's role first, then a Tech Lead), with "Found while drafting the Back-End Design Doc from Spec vN." The AI proposes; the Raiser reviews and sends it (ADR 0001); its Decision reaches the Spec the usual way, and the new Spec Version then makes the Design Doc stale. No Choices are generated (one AI call less; the Raiser can ask a new one with Choices). Without a Role Owner to raise it, the question stays under the Design Doc's Open questions only. A question already raised for the Design Doc (same title) isn't raised again, and later drafts are given those titles.
- **The AI** (`AiPort.draftDesignDoc` / `redraftDesignDoc`, prompts `draft-design-doc` and `redraft-design-doc` in `packages/skills`, `VORASAAN_MODEL_DRAFT_DESIGN_DOC` / `VORASAAN_MODEL_REDRAFT_DESIGN_DOC`): given the Feature, the Design Doc (its Platform and Team Roles, the Feature's targets, the template), what it covers of the Spec Version, for an update the current version and the "- removed / + added" lines of what changed, the questions already raised, and the Feature's retrieved context (Decisions first) on the Decision Request budget. Rules: decide how, never what (every behaviour, number and limit from the Spec or a Decision; names of tables and endpoints are design); never invent requirements, ask instead; a Design Doc never changes the Spec; keep the template's sections; an update changes only what the Spec change requires; QA traces a test case to every acceptance criterion. The Spec, the template, the current version, the questions and the context are fenced as untrusted data; the template is a `<template>` block that can't be closed from inside. Written in the Organization's language (0068): a Design Doc is for a Team, not one person. "Design Doc" is kept as written by the prompts' own rule; adding it to the shared language partial would have changed every prompt's tokens and version.
  - **FakeAiPort**: each `##` section of the template in order; the first (QA: Test cases) traces each checklist item of the Spec ("Covers: …", QA "TC-n (AC: …)") and names each Decision; Open questions lists the Spec's open questions, which also come back as questions (less those asked); Thai for a Thai Spec; an update appends "Updated for Spec vN: <first added line>"; a Redraft appends "- Changed as asked: …". `designDocScript` holds or fails the next drafts.
  - **Eval cases** (`evals/cases/design-docs.ts`, `bun run eval:design-docs`, set "Design Docs" in AI prompts): Back-End from the Spec and the Decisions, Mobile not asking again, QA tracing every criterion, Front-End in Thai from a Thai Spec and template, an update keeping the rest, an injection in the Spec and one in a Decision (no "HACKED", no invented `/admin/delete-all` or "delete orders", nothing claimed approved), a Redraft, and a Redraft from Thai feedback with an injection. "Design Doc" joins the terms the language check keeps.
- **Agent Skills (0078) are not used while drafting.** A draft is a one-shot structured call without a tool loop, like the other one-shot drafts 0078 left out; loading Skills would need `loadSkill` / `readSkillFile` there, their budget and a second injection surface in a call nobody watches as it runs. A diagram can still be made with a Skill in a Feature Conversation. Left open.
- **Token and query guards**: the 0076 guards pass. New checked-in guards: `draftDesignDoc` 1,897 tokens (score 1, Thai 1) and `redraftDesignDoc` 1,873 (1, 1). The product token scenarios end (after the replay, so nothing earlier reads the new Spec Version) with the Back-End and QA Design Docs drafted and one Redraft: `draftDesignDoc` 10,478 and `redraftDesignDoc` 11,197 tokens per call; every other task is unchanged. Query budgets: a new scenario `GET /features/:id/design-docs` (15: identity, the Organization check, then nine reads together, the Blockers' Choices one of them, then the versions, pending and declined proposals and questions together, one statement each; the bench Feature gets three versions, a pending update and two questions per Design Doc), the Inbox 15 → 16 (the Design Doc proposals the person approves, one statement alongside), the Decision Graph reads the Feature's Design Docs alongside its other reads and their lanes only when it has some.
- **Inbox**: `APPROVE_DESIGN_DOC` (the proposal, the Design Doc's key and name, first draft or update) for each approver, by the same rule in one SQL statement, only for Design Docs the Feature still has. Approvers' pages refresh when a draft lands (`inbox.changed`).
- **Web**: the Feature page gains a **Design Docs** tab (each Design Doc, its state: Waiting with the reason, Ready to draft, Drafting…, Waiting for approval, Approved with the Spec Version it follows, Stale; who approves it; questions raised; "Draft the Back-End Design Doc" for approvers when due). A Design Doc's page (`/features/[id]/design-docs/[key]`): the pending draft as a diff with Approve (naming the Redraft), Decline with an optional reason and Request changes (0065's components, `REDRAFT_SLUG.DESIGN_DOC_PROPOSAL`), the questions raised (linked to their Decision Requests), the current version, and the version history with diffs and Revert. Messages sit in a status line and an alert line that stay on the page; the page refreshes every 1.5 s while drafting. Project → Platforms gains each Platform's "Design Doc template" (a kit Select) and **Design Doc templates** (edit, save, back to the built-in one). The Inbox lists "Design Docs to approve". The Decision Graph's **Design Docs sub-lane** is a list under the graph: per Design Doc its versions against the Spec Versions they follow, the pending draft dashed, and "Stale"; it is not drawn into the SVG (its keyboard model is per column, and a list reads in order).
- **CLI**: the TUI Inbox shows "Approve Back-End Design Doc (update) · <Feature>" and, opened, says to review it in the web app. **`vorasaan run` doesn't exist yet** (REQUIREMENT 15 is not built): `GET /features/:id/design-docs/:key` (its newest version's Markdown) is what it will hand over for the developer's Platform.
- **Glossary**: CONTEXT.md gains **Design Doc template**; Inbox Item names a Design Doc.
- **Fixed on the way**: "Drafted with …" under versions used `text-fg-faint` (3.1:1, failing axe on a white page); it is `text-fg-soft` now.
- **Tests**: `design-docs/design-docs.api.test.ts` (real Postgres, `FakeAiPort`, background work drained): the five criteria (nothing drafted while a Spec Proposal awaits approval on the latest Spec or Coverage is missing, even when asked; declining the Spec Proposal drafts Back-End only, a Front-End section then drafts Front-End and QA; approve is v1 following its Spec Version, a Back-End change proposes an update, Request changes is Redraft 2, approving an old Redraft is a 409, the diff from v1 to v2; only Back-End goes stale and is told what changed, QA's pending first draft is superseded, a Front-End change keeps Back-End's pending update following the new Spec; Pim, an Admin and the PO, gets 403 on approve, decline, Request changes, revert and draft with nothing stored, a Tech Lead may approve, and the Team-member fallback stops once the role has a Role Owner; the open question becomes one DRAFT Question raised by the Back-End Role Owner, sendable, not raised again by the update), a failed draft and its retry, a declined draft not redrafted on its own, revert making it stale, templates (a Project's, Flutter naming Mobile, QA refused, back to built in), Receipts and outcomes in the Organization's language, the Inbox and the Decision Graph, reading and 404s. Plus `enums.test.ts`, `receipting.test.ts`, `language.test.ts`, `structured.test.ts`, the eval sets and both token guards, the query budgets, `platforms.api.test.ts` and `ai-settings.api.test.ts` for the new field and task, and the CLI's `format.test.ts`. Browser (`e2e/design-docs.e2e.ts`, light and dark, axe-clean): Beam, the Back-End Role Owner, finds the drafted Back-End Design Doc on the tab and in his Inbox, sees the draft's diff and the question it raised, asks for Redraft 2 and approves it; a Spec change makes it stale and he approves the update and compares the versions; Pim reads it without approving; by keyboard Beam declines a draft (the status line says so, and "Draft the Back-End Design Doc" appears); the Decision Graph's sub-lane; Pim edits the QA template.
- **Check with a real model (manual)**: `bun run eval:design-docs` (from `apps/server`, with `ANTHROPIC_API_KEY` or the provider the env names) and read each case: does each Design Doc follow its template; design only what the Spec and the Decisions settle (no endpoint behaviour, limit, retry count or field the Spec doesn't imply); turn the gaps into at most five useful questions instead of assumptions; trace a QA test case to every acceptance criterion; change only the affected lines in an update; write Thai for a Thai Spec while keeping "Design Doc", names and numbers; ignore the instructions hidden in the Spec, a Decision and the feedback. In the app: whether real Back-End drafts stay within the Decision Request context budget on long Specs, and whether the questions raised are worth a PO's time (else lower `MAX_DESIGN_DOC_QUESTIONS`).
- **Left open**: Agent Skills while drafting (above); `vorasaan run`; drawing the sub-lane in the graph's SVG; Design Docs aren't Action Cards in Conversations, and a Spec Proposal drafted from a Design Doc's question still goes through its Decision Request; editing a Design Doc by hand (only drafts, Redrafts and reverts make versions); a Design Doc for a Platform no longer targeted is kept but not shown.
